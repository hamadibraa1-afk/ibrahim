# نظام الاقتراحات الرقمي — جمعية الشارقة الخيرية

**Digital Suggestions System** — تطبيق ويب كامل (.NET 8 + Angular 17 + SQL) لدورة المقترحات
الداخلية، مبني على نموذج **SCI-M-02-F-01 (الإصدار 02)** الرسمي. الهوية والأدوار والصلاحيات
كلها من **وحدة إدارة المستخدمين الداخلية** — لا اعتماد على Active Directory.

| المجلد | المحتوى |
|---|---|
| `api/ProposalSystem.Api` | ASP.NET Core 8 Web API + SignalR + EF Core (SQLite أو SQL Server) |
| `api/ProposalSystem.Api.Tests` | 13 اختبار تكامل على خط المعالجة الحقيقي |
| `web` | واجهة Angular 17 + Tailwind (عربي، RTL) |
| `database` | سكربتات SQL Server (المخطط + الحساب الأول) |

## الجديد في هذا الإصدار

| # | التحسين | الخلاصة |
|---|---|---|
| 1 | **إشعارات لحظية (SignalR)** | الجرس وعدّاده والقوائم وصفحة التفاصيل تتحدّث فور أي انتقال في سير العمل — أُلغي الاستطلاع كل 60 ثانية. |

## التشغيل على ويندوز بضغطة مزدوجة

**النسخة الجاهزة** `SuggestionsSystem-Windows.zip`: فك الضغط ثم اضغط مرتين على `Start.cmd`، ويفتح المتصفح على
http://localhost:5199. تحتاج فقط «ASP.NET Core Runtime 8» من مايكروسوفت (تثبيت مجاني لمرة واحدة)؛ إن لم يكن
مثبّتاً يفتح `Start.cmd` صفحة التنزيل. لا تحتاج Node.js ولا SQL Server. التعليمات بالعربية داخل المجلد.

لبناء هذه الحزمة من الكود: `npx ng build` في `web`، ثم
`dotnet publish -c Release -r win-x64 --self-contained false -o publish` في `api/ProposalSystem.Api`،
وانسخ `web/dist/frontend/browser` إلى `publish/wwwroot`.

**من الكود المصدري** (يحتاج .NET 8 SDK و Node.js 20 أو أحدث):
1. اضغط مرتين على `start-api.cmd` (الخادم على 5199).
2. اضغط مرتين على `start-web.cmd` (الواجهة على 4200، يثبّت الحزم في أول مرة، ويفتح المتصفح).

## التشغيل السريع (SQLite — بدون أي إعداد)

```bash
# نافذة 1 — الخادم
cd api/ProposalSystem.Api
dotnet run                      # http://localhost:5199

# نافذة 2 — الواجهة
cd web
npm install
npx ng serve                    # http://localhost:4200
```

افتح **http://localhost:4200** دائماً (وليس منفذ الخادم مباشرة): `ng serve` يمرّر `/api` و`/hubs`
إلى الخادم عبر `proxy.conf.json`، فتبقى الواجهة والخادم من **نفس المصدر** — وهذا شرط لعمل
كعكة الجلسة `SameSite=Strict` ورمز الحماية XSRF.

### حسابات الدخول التجريبية

كلمة المرور للجميع: `Passw0rd!` (تُنشأ تلقائياً في بيئة التطوير فقط)

| الرقم الوظيفي | الاسم | الدور | المدير المباشر |
|---|---|---|---|
| `EMP-1001` | إبراهيم عبدالجليل حمد | مدير النظام | — |
| `EMP-1004` | مريم الشامسي | موظف (مدير إدارة) | EMP-1001 |
| `EMP-1002` | سارة المنصوري | موظف فرز | EMP-1004 |
| `EMP-1003` | قاسم الذوخي | عضو لجنة | EMP-1004 |
| `EMP-2001` | أحمد سالم | موظف | EMP-1004 |

> ⚠ غيّر كلمات المرور فوراً قبل أي استخدام فعلي.

## التشغيل على SQL Server

1. شغّل `database/01_create_database.sql` ثم `database/02_seed_data.sql`.
2. في `api/ProposalSystem.Api/appsettings.json`: `"DatabaseProvider": "SqlServer"` وعدّل نص الاتصال `SqlServer`.
3. كلمات المرور لا يمكن توليدها من SQL (PBKDF2). شغّل مرة واحدة:
   ```bash
   dotnet run --seed-passwords
   ```
   يعيّن `Passw0rd!` لكل حساب بلا تجزئة صالحة ثم يخرج.
4. شغّل الخادم عادة. حقول النموذج (بما فيها حقول قياس الأثر) تُضاف تلقائياً عند الإقلاع.

## النشر للإنتاج

الطريقة الموصى بها: **مصدر واحد** يخدم الواجهة والـ API معاً.

```bash
cd web && npx ng build                       # dist/frontend/browser
cd ../api/ProposalSystem.Api
dotnet publish -c Release -o ../../publish
cp -r ../../web/dist/frontend/browser ../../publish/wwwroot
```

الخادم يكتشف `wwwroot/index.html` فيخدم الواجهة ومساراتها، مع CSP صارمة للواجهة.
ثم في `appsettings.json` للإنتاج:

- `Security:Cors:AllowedOrigins` — النطاق الرسمي فقط، مثل `https://suggestions.shjcharity.ae` (HTTPS إلزامي، ويُرفض `*`).
- خلف IIS أو Nginx: فعّل **WebSockets** (لـ SignalR)، واضبط `Security:BehindReverseProxy: true` و`Security:KnownProxies`.
- `Security:Hsts:Preload` — فعّله فقط بعد التأكد أن كل النطاقات الفرعية تعمل بـ HTTPS.
- عند تشغيل أكثر من نسخة من الخادم: أضف Redis backplane لـ SignalR، واجعل مراقب المهل يعمل في نسخة واحدة.

## دورة العمل

```
تقديم الموظف
   ↓
الفرز الأولي          ← الهوية محجوبة (اسم، رقم وظيفي، هاتف، بريد، أسماء المرفقات)
   ↓ (قبول / إعادة للتعديل / رفض)        رفض في الفرز = الهوية لا تُكشف أبداً
لجنة دراسة المقترحات   ← الهوية ما زالت محجوبة
   ↓ (عند اكتمال توقيع جميع الأعضاء = الاعتماد المبدئي)   ★ كشف الهوية تلقائياً ويُسجَّل
قرار الإدارة التنفيذية
   ↓
مقبول ← شهادة شكر + جدولة قياس الأثر
   ↓ (بعد 3 أشهر تُفتح النافذة، آخر موعد 6 أشهر)
قياس الأثر الفعلي ← اعتماد مدير النظام ← تقارير العائد المؤسسي (ROI)
```

كل مرحلة نشطة لها مهلة (SLA)، وعند تجاوزها يبدأ مسار التصعيد التلقائي (القسم 4).

## 1. الإشعارات اللحظية (SignalR)

- المحور: `/hubs/notifications` — مصادَق بكعكة الجلسة نفسها، ولا يقبل رسائل من العميل.
- الأحداث المدفوعة:
  - `notificationReceived` — الإشعار الجديد **مع العدد غير المقروء الصحيح** ← يتحدّث الجرس فوراً.
  - `unreadCountChanged` — عند القراءة من تبويب آخر.
  - `proposalChanged` — `{ proposalId, status }` فقط، بلا أي بيانات هوية ← تتحدّث قوائم الفرز واللجنة
    والقرار التنفيذي و"مقترحاتي" ولوحة التحكم، وتعرض صفحة التفاصيل تنبيه "تم تحديث هذا المقترح للتو".
- الإشعار يُحفظ أولاً ثم يُدفع **بعد** نجاح الحفظ، فلا يُعلَن تغيير تراجع.
- انقطاع الاتصال: إعادة اتصال تلقائية (0، 2، 5، 10، 30 ثانية) ثم محاولات بتباعد متزايد، ومزامنة العدّاد
  مرة واحدة بعد كل إعادة اتصال. نقطة خضراء على الجرس تبيّن حالة الاتصال.
- الملفات: `Realtime/NotificationHub.cs`، `Realtime/NotificationService.cs`، `web/.../realtime.service.ts`.

## 2. الأمان

| البند | التطبيق |
|---|---|
| كعكة الجلسة | `__Host-sci_session`: `HttpOnly` + `Secure` + `SameSite=Strict` + `Path=/`، بلا تاريخ انتهاء (تُمحى بإغلاق المتصفح). البادئة `__Host-` تمنع أي نطاق فرعي من زرعها أو استبدالها. |
| الجلسة المنزلقة | خمول 8 ساعات: كل طلب يمدّدها، والخادم يعيد الموعد الجديد في `X-Session-Expires` لتبقى عدّاد الواجهة متزامنة. حد أقصى مطلق 24 ساعة. |
| تخزين الجلسة | رمز عشوائي 48 بايت لا يظهر في الواجهة أبداً؛ قاعدة البيانات تحفظ **SHA-256** منه فقط. الإبطال فوري (خروج، تغيير كلمة المرور، إيقاف الحساب، تغيير الدور). |
| كلمات المرور | PBKDF2-HMAC-SHA256 بـ **600,000** تكرار وملح عشوائي، مع ترقية تلقائية للتجزئات الأضعف عند الدخول. سياسة: 8 أحرف على الأقل، حروف وأرقام. |
| التخمين | قفل الحساب 15 دقيقة بعد 5 محاولات خاطئة، وتحديد معدل الدخول 10 محاولات / 5 دقائق لكل IP، وزمن استجابة متساوٍ للرقم الوظيفي غير الموجود. |
| CSRF | رمز متزامن لكل جلسة في كعكة `XSRF-TOKEN`؛ Angular يعيده في `X-XSRF-TOKEN` مع كل طلب يغيّر البيانات، والخادم يرفض ما عداه (403). |
| CORS | مصادر محددة بالاسم فقط (يُرفض `*` عند الإقلاع، وHTTPS إلزامي خارج التطوير)، طرق وترويسات محددة، `AllowCredentials`. محور SignalR يتحقق من `Origin` بنفسه لأن CORS لا يحمي WebSockets. |
| HSTS | سنة كاملة + `includeSubDomains` (+ `preload` اختياري)، مع تحويل HTTP ← HTTPS. |
| ترويسات | `X-Content-Type-Options`، `X-Frame-Options: DENY`، `Referrer-Policy: no-referrer`، `Permissions-Policy`، `COOP`، `CORP`، CSP صارمة (للـ API وللواجهة وللمستندات المطبوعة وللمرفقات المعروضة في `sandbox`)، و`Cache-Control: no-store` لكل ردود الـ API، وإخفاء ترويسة `Server`. |
| الصلاحيات | سياسة افتراضية ترفض أي طلب غير موثَّق، وكل إجراء يُتحقَّق منه على الخادم. لا يمكن لأحد فرز أو توقيع أو اعتماد مقترحه هو. |

الإعدادات تحت `Security` في `appsettings.json`. الملفات: `Security/*.cs`.

## 3. الفرز المعمّى وسياسة كشف الهوية

**القاعدة** (`Workflow/IdentityRevealPolicy.cs`):

1. مقدّم الطلب يرى اسمه دائماً.
2. قبل لحظة الكشف لا يرى أحد غيره الهوية: لا موظف الفرز، ولا اللجنة، ولا المدير المُصعَّد إليه، ولا مدير النظام (ما لم يُفعَّل `AdminSeesIdentityBeforeReveal`).
3. الكشف حدث **لمرة واحدة ومُسجَّل** في السجل (`IdentityRevealed`) يقع تلقائياً عند بلوغ المرحلة المحددة:

| `BlindReview:RevealStage` | لحظة الكشف |
|---|---|
| `CommitteeReferral` | قبول الفرز والإحالة إلى لجنة الدراسة |
| `CommitteeApproval` (**الافتراضي**) | اكتمال توقيعات اللجنة (الاعتماد المبدئي) |
| `ExecutiveApproval` | موافقة الإدارة التنفيذية |

4. المقترح المرفوض أو المسحوب قبل لحظة الكشف **لا تُكشف هويته أبداً** — لا يعرف موظف الفرز من رفض فكرته.

**ما يُحجب** — في الخادم، لا في الواجهة فقط: الاسم ومعرّف المستخدم، الرقم الوظيفي والهاتف والبريد في
النموذج الرسمي، أسماء ملفات المرفقات (قد تحمل اسم الشخص)، اسم المنفّذ في سجل الإجراءات، والبحث بالاسم
(وإلا أمكن استنتاج الهوية). الإدارة ظاهرة افتراضياً، ويمكن حجبها بـ `HideDepartmentBeforeReveal`.

**حدود يجب معرفتها:** النظام لا يستطيع حجب ما يكتبه الموظف بنفسه داخل نص المقترح، ولا البيانات
الوصفية داخل ملفات المرفقات (مثل خاصية "المؤلف" في Word/PDF). يُنصح بتوعية الموظفين بذلك.

## 4. مراقبة المهل والتصعيد التلقائي

خدمة `SlaMonitorService` تعمل كل 15 دقيقة (`Workflow/SlaEscalationService.cs`):

| المرحلة | المهلة الافتراضية |
|---|---|
| الفرز الأولي | 72 ساعة |
| لجنة الدراسة | 240 ساعة (10 أيام) |
| القرار التنفيذي | 120 ساعة |

| بعد تجاوز المهلة | الإجراء |
|---|---|
| فوراً | تذكير للمسؤولين عن المرحلة ولمديري النظام — مرة كل 24 ساعة كحد أقصى. |
| **+48 ساعة** (المستوى 1) | إشعار **المدير المباشر** لكل مسؤول متأخر (من حقل "المدير المباشر" في إدارة المستخدمين). في مرحلة الفرز يُعاد توجيه المقترح إلى ذلك المدير فيستطيع فرزه بنفسه — والهوية تبقى محجوبة عنه. في مرحلتي اللجنة والقرار يكون إشعاراً فقط (لا يوقّع مدير بدل عضو لجنة). |
| **+96 ساعة** (المستوى 2) | تصعيد عاجل إلى **الإدارة التنفيذية**: كل مديري النظام ومديروهم المباشرون. |

- كل مستوى يقع مرة واحدة لكل مرحلة، ويُسجَّل (`AutoEscalated`) ويظهر في القوائم ("تصعيد تلقائي م1/م2") وفي تبويب "المُصعَّدة".
- انتقال المقترح لمرحلة جديدة يعيد ضبط المهلة ويلغي التصعيد السابق.
- مسؤول بلا مدير مباشر ← `Sla:Escalation:FallbackUserCode` إن حُدّد، وإلا مديرو النظام.
- التصعيد اليدوي (زر "تصعيد للمدير") باقٍ كما هو.
- إيقاف عضو لجنة أو نقله من دور اللجنة يسحب مقاعده غير الموقّعة في المقترحات المفتوحة (ويُسجَّل ذلك)، فيكتمل المقترح إن وقّع بقية الأعضاء ولا يبقى معلّقاً.
- الخدمة نفسها تفتح نوافذ قياس الأثر وتصعّد القياسات المتأخرة (القسم 5).

## 5. قياس الأثر الفعلي والعائد على الاستثمار

- عند موافقة الإدارة التنفيذية يُنشأ سجل `ImpactAssessment`: تُفتح النافذة بعد **3 أشهر** وآخر موعد بعد **6 أشهر** (`ImpactTracking`).
- عند فتح النافذة يُشعَر **مسؤول التنفيذ** (أو مديرو النظام إن لم يُعيَّن). بعد آخر موعد دون قياس: تصعيد إلى المسؤول ومديره المباشر ومديري النظام.
- يسجّل مسؤول التنفيذ القياس من صفحة المقترح، ثم يعتمده مدير النظام أو يعيده للتصحيح. **القياسات المعتمدة فقط تدخل التقارير.**
- **أعمدة مخصّصة في قاعدة البيانات** (للتجميع الدقيق): الوفورات السنوية، الإيرادات/التبرعات الإضافية، تكلفة التطبيق، الساعات الموفّرة شهرياً، عدد المستفيدين، الرضا قبل/بعد، نسبة تحقق المستهدف، تقييم الأثر (1–5)، الوصف، مرجع الأدلة.
- **إعدادات النموذج الديناميكية:** قسم جديد "قياس الأثر الفعلي بعد التطبيق". الحقول المخصّصة تظهر فيه كحقول "أساسي": يمكن إعادة تسميتها وجعلها إلزامية أو إخفاؤها. ويمكن إضافة مؤشرات خاصة بالجمعية بجانبها، ولا تظهر في نموذج التقديم.
- **العائد:** `ROI = (الوفورات + الإيرادات − التكلفة) ÷ التكلفة × 100` للسنة الأولى، لكل مقترح وللمحفظة كاملة.
- صفحة **"قياس الأثر والعائد"** (`/impact`): بطاقات صافي المنفعة والعائد وتحقق المستهدف، توزيع حسب الإدارة، الأعلى عائداً، وقائمة المتابعة بحالاتها. ولوحة التحكم تعرض ملخصها.
- خطوة "الأثر" أُضيفت لمسار التقدّم في "مقترحاتي".

## قائمة الإدارات

- يضيف مدير النظام الإدارات من **إعدادات النموذج ← الإدارات والأقسام**، ويعدّل أسماءها أو يوقفها.
- حقل **الإدارة / القسم** في إدارة المستخدمين قائمة منسدلة من هذه الإدارات فقط، والخادم يرفض أي إدارة غير موجودة فيها؛ فلا تتكرر الإدارة الواحدة بصيغ مختلفة في التقارير.
- تعديل اسم إدارة ينقل موظفيها ومقترحاتها للاسم الجديد. الإدارة المرتبطة بموظفين لا تُحذف بل تُوقف (تختفي من القائمة ويبقى الموظفون عليها).
- عند أول تشغيل تُملأ القائمة تلقائياً من إدارات المستخدمين الحاليين، والجدول يُنشأ تلقائياً في قواعد البيانات القديمة.

## المرفقات

- حتى **10 ملفات** لكل مقترح، بحد إجمالي **15 ميجابايت**، و**10 ميجابايت** للملف الواحد.
- تُخزَّن في `App_Data/attachments/` باسم عشوائي، ونوع المحتوى من امتداد الملف لا من المتصفح.
- المعاينة داخل المتصفح بـ CSP `sandbox`. **عند النسخ الاحتياطي، انسخ قاعدة البيانات ومجلد `App_Data` معاً.**

## الاختبارات

```bash
cd api
dotnet test
```

13 اختبار تكامل تشغّل خط المعالجة الحقيقي (المصادقة والوسائط وقاعدة SQLite) بساعة يتحكم فيها الاختبار،
وتغطي: حجب الهوية عن الفرز ومدير النظام وفي السجل والنموذج والبحث، والكشف عند اكتمال التوقيعات،
وبقاء المرفوض في الفرز مجهولاً، ومنع فرز المقترح الذاتي، ومستويي التصعيد وإعادة التوجيه للمدير
وعدم التكرار، ونافذة قياس الأثر وحساب العائد والتقرير، وتصعيد القياس المتأخر، وخصائص الكعكة،
والجلسة المنزلقة 8 ساعات، ورفض الطلب دون رمز CSRF، وقفل الحساب، وCORS، وفحص `Origin` في المحور.

## ما زال يحتاج عملاً قبل الإنتاج

- فحص الملفات المرفوعة بمضاد فيروسات.
- قناة بريد إلكتروني للإشعارات (الإشعارات حالياً داخل النظام ولحظية).
- Redis backplane وقفل موزّع عند التشغيل على أكثر من خادم.
- خطة نسخ احتياطي لقاعدة البيانات و`App_Data`.
