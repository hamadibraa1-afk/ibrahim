# قواعد العمل المشتركة — Claude و Codex

> هذا الملف هو المرجع الوحيد للقواعد. يقرؤه **Codex** تلقائياً (AGENTS.md)، ويقرؤه **Claude** عبر `CLAUDE.md` الذي يستورده.
> أي تعديل على القواعد يتم هنا فقط، ويُذكر في `COLLAB.md`.

## 1. تعريف المشروع

**نظام الاقتراحات والشكاوى الرقمي — جمعية الشارقة الخيرية.**

> العمل الجاري: نظام دخول مزدوج (حسابات دومين + حسابات محلية) + تطبيق مكتبي بدخول تلقائي + نظام الشكاوى.
> المواصفة الملزمة: **`docs/SPEC_AUTH_COMPLAINTS.md`** — اقرأها قبل أي عمل على هذه المحاور.

يدير دورة مقترح الموظف بالكامل:

```
تقديم → فرز أولي (معمّى) → لجنة الدراسة (دراسة + توصية + توقيعات) → قرار الإدارة التنفيذية → قياس الأثر بعد 3–6 أشهر
```

| الطبقة | التقنية | المسار |
|---|---|---|
| الخادم | ASP.NET Core 8 Web API + EF Core (SQLite افتراضياً، SQL Server اختيارياً) | `api/ProposalSystem.Api` |
| الاختبارات | xUnit + WebApplicationFactory (28 اختبار تكامل) | `api/ProposalSystem.Api.Tests` |
| الواجهة | Angular 17 (standalone components، Tailwind، تصميم Glassmorphism، RTL عربي) | `web/` |
| قاعدة البيانات | سكربت SQL Server الكامل | `database/01_create_database.sql` |
| التشغيل على ويندوز | `start-api.cmd` (http://localhost:5199) و `start-web.cmd` | الجذر |
| التطبيق المكتبي (قيد البناء) | .NET 8 WPF + WebView2، دخول تلقائي بالويندوز | `desktop/SuggestionsDesktop` |

**الأدوار:** موظف `Employee` · موظف فرز `Screener` · عضو لجنة `CommitteeMember` · مدير تنفيذي `Executive` · موظف فرز الشكاوى `ComplaintScreener` · مدير نظام كامل `Admin`. تُحدَّد من داخل المنصة.

### خريطة الخادم
- `Workflow/ProposalAccess.cs` — **كل** صلاحيات المقترح (من يرى/يعدّل/يفرز/يوقّع/يقرر) + `EnterStage` (بدء مرحلة ومهلتها).
- `Workflow/IdentityRevealPolicy.cs` — المراجعة المعمّاة وقاعدة كشف الهوية.
- `Workflow/SlaEscalationService.cs` — التذكير والتصعيد التلقائي (مستوى 1 بعد 48 ساعة من المهلة للمدير المباشر، مستوى 2 بعد 96 ساعة للإدارة التنفيذية) + نوافذ قياس الأثر.
- `Workflow/CommitteeProgress.cs` — متى تكتمل مرحلة اللجنة.
- `Controllers/` — الـ API. `ProposalsController` هو قلب سير العمل، `ImpactController` للعائد على الاستثمار.
- `Security/` — جلسة بكوكي HttpOnly + CSRF (`XSRF-TOKEN`/`X-XSRF-TOKEN`) + PBKDF2.
- `Realtime/` — SignalR `/hubs/notifications` والإشعارات.
- `Data/SchemaUpgrader.cs` — يضيف الجداول الناقصة لقواعد البيانات القديمة.

## 2. ثوابت لا تُكسر (أي تغيير يخالفها = خطأ حرج)

1. **المراجعة المعمّاة:** لا يظهر اسم مقدّم المقترح ولا رقمه ولا هاتفه ولا بريده ولا أسماء ملفاته (ولا إدارته إن كان `HideDepartmentBeforeReveal` مفعلاً) لأي مراجع قبل `IdentityRevealedAt`. هذا يشمل: DTO، المستندات المطبوعة، سجل التدقيق، البحث والفلترة، الإشعارات.
2. **لا أحد يفرز أو يوقّع أو يقرر على مقترحه هو.**
3. **الصلاحيات تُفحص في الخادم دائماً** (`ProposalAccess`)؛ الواجهة تعرض فقط ما يرسله `actions`.
4. **الانتقال بين المراحل يتم عبر `EnterStage` فقط** (يعيد ضبط المهلة والتصعيد).
5. **أرقام قياس الأثر تدخل التقارير بعد اعتمادها (Verified) فقط.**
6. **الأمان:** لا توكن في جسم الاستجابة، لا CORS بنجمة، لا تعطيل CSRF، لا كلمات مرور أو أسرار في الكود أو السجلات.
7. **الدخول:** رسالة فشل عامة واحدة لكل الحالات، لا كلمات مرور مخزنة لحسابات الدومين، لا كلمات مرور افتراضية أو معروفة، والحساب المحلي لا يدخل من التطبيق المكتبي.
8. **الشكاوى:** هوية مقدّم الشكوى بدون اسم لا تظهر لأي أحد غيره (ولا لمدير النظام)، والمشتكى عليه لا يرى الشكوى ولا يعالجها.
9. **النصوص الظاهرة للمستخدم بالعربية**، والواجهة RTL، ويُحافَظ على تصميم Glassmorphism والصور الموجودة.

## 3. طريقة العمل بالتزامن

### القيادة: Codex يدير العمل
بقرار صاحب المشروع، **Codex هو مدير العمل (Lead)** وClaude يعمل بالتنسيق معه:

| | Codex (مدير العمل) | Claude |
|---|---|---|
| ترتيب المهام وتوزيعها | يقرر ويكتب المهام في `COLLAB.md` («المهام المسندة») مع معيار القبول لكل مهمة | ينفّذ ما يُسند له في منطقته، ويبلّغ بالنتيجة في `COLLAB.md` |
| تغييرات عقد API | يعتمد أو يرفض المقترحات (بعد سماع رأي Claude) ويحدّث المواصفة | يقترح ويعلّق |
| الخلاف الفني | يحسمه، ويسجّل القرار وسببه في «القرارات» | يعرض رأيه مع الدليل قبل الحسم |
| إغلاق المرحلة | يعلن اكتمالها بعد نجاح كل الفحوص ومعايير القبول | يؤكد نجاح فحوص الخادم |

حدود القيادة (لا يتجاوزها أحد):
- **أمر البدء وأي توسيع للنطاق** من صاحب المشروع فقط.
- الثوابت في القسم 2 والمراجعة المتبادلة إلزامية على المدير أيضاً: عمل Codex يراجعه Claude، وبند 🔴 لا يُغلق إلا بإصلاح أو بقرار مسجّل.
- Claude يستطيع رفض مهمة تخالف ثابتاً أو تكسر الأمان، مع ذكر السبب في `COLLAB.md`، ويُرفع الأمر لصاحب المشروع.

**التواصل:** كل التنسيق مكتوب في `COLLAB.md` عبر git (لا يرى أحدنا محادثة الآخر). Claude يبدأ كل جلسة بقراءة «المهام المسندة» و«بانتظار المراجعة».

### التوزيع الافتراضي
| الوكيل | يملك (يكتب فيه) | يراجع |
|---|---|---|
| **Claude** | `api/` (الخادم والاختبارات) و `database/` | عمل Codex |
| **Codex** | `web/` (الواجهة) و `desktop/` (التطبيق المكتبي) | عمل Claude |

- الملفات المشتركة (`AGENTS.md`, `README.md`, `*.cmd`) تُعدّل بعد حجزها في `COLLAB.md`.
- إذا احتاج أحدكما تعديل ملف في منطقة الآخر: **يحجزه أولاً** في `COLLAB.md` (قسم «الحجوزات»)، ولا يعدّل ملفاً محجوزاً للآخر.

### دورة كل مهمة
1. **اسحب أحدث نسخة** (`git pull`) واقرأ `COLLAB.md`.
2. **احجز** المهمة/الملفات في `COLLAB.md` باسمك.
3. **نفّذ تغييراً صغيراً ومركّزاً**، مع اختبار يغطيه إن كان في الخادم.
4. **تحقق محلياً** (القسم 4) — لا تُرسل شيئاً يفشل.
5. **Commit** برسالة واضحة تبدأ باسمك: `[claude] ...` أو `[codex] ...`.
6. **اطلب المراجعة**: أضف سطراً في «بانتظار المراجعة» في `COLLAB.md` مع رقم الـ commit.
7. **فك الحجز** بعد الانتهاء.

### قواعد المراجعة المتبادلة
- كل commit يراجعه **الوكيل الآخر** قبل اعتباره منتهياً (`git show <sha>`).
- المراجع يكتب النتيجة في `COLLAB.md` بأحد التصنيفات:
  - 🔴 **حرج** — خطأ برمجي، خطأ منطقي، ثغرة، أو كسر لثابت من القسم 2 → يجب إصلاحه.
  - 🟡 **ملاحظة** — تحسين مقترح، لا يمنع القبول.
  - ✅ **مقبول**.
- كل ملاحظة 🔴 تُكتب بصيغة: **الملف:السطر — المشكلة — سيناريو يثبتها — الإصلاح المقترح**. لا نتائج بلا دليل.
- صاحب الكود يصلح أو يرد بسبب واضح. لا يُغلق بند 🔴 إلا المراجع.
- **لا تعيد كتابة عمل الآخر بدون بند مراجعة**، ولا تحذف اختبارات أو تعطّلها لتمرير البناء.

### عقود API
- عقد API في `docs/SPEC_AUTH_COMPLAINTS.md` هو الاتفاق بين الخادم والواجهة. كل طرف يبني عليه بالتوازي.
- أي تغيير في العقد: يُقترح في `COLLAB.md` (قسم «تغييرات العقد»)، ويوافق عليه الطرف الآخر، ثم يُحدَّث ملف المواصفة.
- Codex يستطيع بناء الواجهة قبل جاهزية الخادم بالاعتماد على العقد، ثم يختبر عليه فور دمجه.

## 4. أوامر التحقق (إلزامية قبل كل commit)

```bash
# الخادم: بناء + 28 اختبار (يجب أن تنجح كلها)
cd api && dotnet test

# الواجهة: بناء إنتاجي بدون أخطاء
cd web && npm ci && npx ng build

# التطبيق المكتبي (على ويندوز)
cd desktop && dotnet build
```

تشغيل يدوي: `start-api.cmd` ثم `start-web.cmd` (أو `dotnet run --launch-profile http` في `api/ProposalSystem.Api` و `npx ng serve` في `web`).
ملاحظة: رسائل `UNIQUE constraint failed: Proposals.ProposalCode` في مخرجات الاختبارات متوقعة (اختبار التقديم المتزامن).

## 5. أسلوب الكود
- طابق أسلوب الملف المحيط: التسمية، كثافة التعليقات، والأنماط (records للـ DTO، `ApiException` للأخطاء، `AuditTrail` لكل إجراء، `NotificationService` للإشعارات).
- كل إجراء يغيّر حالة المقترح يُسجَّل في التدقيق ويُرسل إشعاراً لمن يعنيه، ويستثني مقدّم المقترح من إشعارات المراجعين.
- في الواجهة: standalone components، signals حيث هي مستخدمة، وخدمات `core/services` للاتصال بالـ API.
- لا تضف مكتبات جديدة بدون ذكر السبب في `COLLAB.md`.
